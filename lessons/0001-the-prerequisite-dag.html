1 · Why "nuclear bomb" — the significance layer

Strip the hype from the HN front-page thread and four real claims remain. Each one is checkable against the repo's own doc/inference_deployment_qa.md.

S1They published their margins

One cluster serves 155 trillion tokens/day; overall revenue is US$38 per GPU-hour "at valley pricing" (Q&A §overview). Frontier labs publish price lists, not actual earnings per GPU-hour. When a price leader discloses unit revenue, every inference vendor's spreadsheet becomes guesswork-if-generous.

HN did the math immediately: at ~26k tok/s/GPU the benchmark implies roughly tens of thousands of GPUs just to match the token claim — one comment thread redoing it. Either number, taken alone, reframes what a token should cost.

S2 The best operator dumped its production stack

DeepInfer is the serving code behind a model that hundreds of millions use, self-reported as built on vLLM with ideas from SGLang and TensorRT-LLM (README §acknowledgments). The companies selling "we serve models better than you can" (Together, Fireworks, Baseten, DeepInfra…) now compete against their own best supplier's free code — with the originators saying inference code for future DeepSeek models continues landing here (Q&A §1).

S3 Frontier serving, dual-hardware, sanctioned-proof

Builds run on both NVIDIA SM100 and Huawei Ascend 950 — with full kernel-port twins (vendor/DeepGEMM-Ascend, vendor/DeepEP-Ascend, deepinfer/npu_ops/). That is public evidence that frontier-grade inference has been ported off NVIDIA silicon, down to the kernels. Combined with DeepSeek's low energy costs (HN threads on China infrastructure), the release reads as an economic statement about where serving can live.

S4 FP4 at production scale

The Q&A states the formats plainly: main KV cache per-16 e4m3 (NVFP4-style minus global scale), indexer KV and MoE routed-expert weights per-32 ue8m0 MXFP4, SWA KV in MXFP8 (528 B/token). 4-bit KV at trillion-token/day scale is an economics claim as much as a numerics one — decode is memory-bandwidth-bound (node A1), so halving bits ~doubles the wall you hit first.

S5 The skeptic's card (always carry one)

The "bomb" framing deserves counterweight: benchmarks are self-reported on their own hardware (examples/benchmark.py, examples/sweep/run_sweep.sh); the Q&A admits public FlashMLA lacks one hand-tuned SASS optimization making decode kernels 5–10% slower than internal, with end-to-end within ~5% (Q&A §kernels). The per-GPU revenue number is "overall revenue at valley pricing" — not a margin statement. Lesson 0006 covers reading these benchmarks honestly.

S6 The open-drops lineage (context you'll be expected to know)

DeepSeek has burned down its library in public once before — FlashMLA, DeepGEMM, DeepEP, 3FS, TileLang, and now deepseek-recipe alongside DeepInfer. Each repo is used by a later lesson: kernels (D3), the KV store (B5), protocol handling (a later peripheral lesson).

2 · Tier A — Serving fundamentals — vocabulary of the whole course

built on: nothing but an API-user's intuition

A1Prefill vs decode: two beasts

Generating one response = prefill (read the whole prompt in parallel; compute-bound, GPU math is starved for work) + decode (produce one token at a time; each step re-reads weights and KV from memory; memory-bandwidth-bound). Nearly every design decision in DeepInfer follows from the fact that these two need different resources — and the repo generalizes that to a third: the vision encoder (VE), producing a VE/Prefill/Decode (EPD) disaggregated architecture (Q&A §overview).

A2KV cache & paged KV

Saving attention's keys/values per layer avoids recomputing the prompt for every token — it is the thing that makes decode cheap and also the thing that eats all memory. Paged KV (vLLM's idea, DeepInfer builds on vLLM) stores it in fixed-size blocks instead of one contiguous slab, removing fragmentation. Both prefill and decode use paged blocks in DeepInfer (Q&A §block KV). Primary source: PagedAttention paper.

A3 SLOs & batching: the Pareto frontier

TTFT (time to first token), TBT/ITL (time between tokens), and throughput trade off against each other; batching raises throughput and hurts TBT. The README's two Pareto plots are that story. Lesson 0006 will make you able to reproduce them with examples/benchmark.py's methodology (its metrics are subtly defined — the README's benchmark section is longer than some papers).

A4The parallelism suite & Wide-EP

Splitting one model across GPUs: DP (replicate, split requests), TP (split each matrix), PP (split by layers), EP (split MoE experts), CP (split sequence context — DeepInfer's "balanced CP"). Rule from the Q&A: prefill uses the smallest EP/DP that HBM allows (2–8); decode uses the largest (64–128, "Wide-EP") to cut per-step memory traffic in the MoE part; TP/CP unused for prefill/decode core. Prefill and decode sitting at opposite ends of that dial is one of the two big reasons they're disaggregated (A1).

A5 MoE anatomy & EPLB

MoE layers route each token to a few routed experts (+ always-on shared expert). Hot experts overload GPUs; EPLB fixes load imbalance with redundant copies of hot experts, re-assigned every N steps from observed load — measured imbalance 1.045–1.09 (slowest/mean) (Q&A §EPLB). DeepSeek is the industry's scale leader here; EP + EPLB is where their throughput advantage concentrates.

A6 Speculative decoding & MTP

Decode one-token-at-a-time wastes the GPU. A tiny draft model (in DeepSeek's case the model's own MTP head — multi-token prediction) guesses several future tokens; the big model verifies them in one forward pass — same quality, more tokens per step. Default: 5 drafts/request (DEEPINFER_USE_NEXTN_DECODE); production acceptance ≈ 3.2–3.3 tokens (Q&A §spec decoding).

A7 Quantization formats you must read

You need vocabulary, not numerics theory: BF16/FP8 baseline; e4m3 = an FP8 layout; ue8m0 = power-of-2 scale exponent; MXFP4 = per-32-element-block 4-bit with shared scale; NVFP4 = NVIDIA's per-16 variant (DeepInfer: "like NVFP4 but without the global scale"). Where each lives: main KV per-16 e4m3; indexer KV & MoE weights per-32 MXFP4; SWA KV MXFP8. (Q&A §low-precision)

3 · Tier B — The machine substrate — why the software is shaped this way

built on: A1 (the two-phase insight), A4 (parallelism)

B1 GPU anatomy & the roofline

SMs do math; HBM supplies data. Tensor-heavy prefill can saturate SMs; decode usually can't — it limps at the HBM bytes/step wall (read every weight + KV per token). This is why node A4's Wide-EP matters: it minimizes bytes moved per decode step. One-line roofline intuition in glossary; enough for this course.

B2 Interconnect: scale-up domains, RDMA, GDR

8–128 GPUs within an NVLink/scale-up domain can move data fast enough for collective-heavy math; across machines use RDMA. DeepInfer specifics worth noticing: KV swap-in uses GDR (RDMA NIC copies to HBM without touching SMs) because CUDA copy engines handle fine-grained KV blocks poorly; cross-machine SWA hits pull over a 400G VLAN; splitting P/D across datacenters is feasible with ~400 Gbps per 8 GPUs (Q&A §cluster/storage, §kv hits).

B3 Execution models: CUDA graphs & async scheduling

CUDA graphs = pre-recorded GPU work sequences that remove launch overhead (worker/cuda_graph_runner.py). Async scheduling (the "zero-overhead batch scheduler") overlaps CPU scheduling of step N+1 with GPU running step N — following SGLang/NanoFlow (Q&A §async). Here's the repo fact that surprised us: the scheduler itself is native code — deepinfer/_C/engine.pyi stubs it out from csrc/engine/; Python only creates it (llm_engine.py::_create_scheduler). The hot loop of a serving engine at this scale is no longer a Python dict walk.

B4 Collectives: all-reduce & all-to-all

Parallel models talk via collectives. MoE's EP gate is all-to-all (each token dispatched to its experts' GPUs and back) — that's DeepEP's whole job. DP load balancing does an all-reduce MIN on quotas each prefill step (Q&A §prefill LB). EPLB shuffles expert weights over NVLink symm_mem. If you've never written a collective, no planned lesson requires it — but you must read them fluently.

B5Storage engineering: the 3FS KV store

The persistent layer: a dedicated 3FS cluster, ~100 PiB of SSD, 10+2 erasure coding, ~40 GB/s read per storage server, LRU GC worker per node; KV blocks stored by kvcache-store; TTL ≈ 3 days (agents) / 7 days (chatbots; long-tail hits make loss expensive — ~0.5–1% hit-rate cost). Design reason to memorize: a dedicated store lets any engine hit any prefix, decoupling prefix affinity from load balancing (Q&A §KV cache storage).

4 · Tier C — The DeepSeek deltas — where this repo is genuinely novel

built on: A2 A4 A6 B3 B5

C1 MLA & FlashMLA — why DeepSeek KV is small

MLA stores attention as a compressed latent instead of per-head K/V — the root of DeepSeek's KV economics, and the reason kernel work concentrates in FlashMLA (one HW branch: "flash" variants handle the windowed SWA case here — see C3). Background lesson 0004.

C2V4.1-Flash architecture: CED/YOCO + SWA + C2

The served model departs from a textbook transformer: CED/YOCO-style split — the decoder's block KV cache is projected from the last encoder layer's hidden state, so decoder KV is cheap to produce; ~20 stored layers use sliding window attention (SWA); "C2 compression" maintains accumulating states (ca_state/ica_state at 128-token boundaries) — DeepSeek's linear-attention-family ingredient; the model also feeds an Engram hash n-gram layer (v4_modules/engram_*.py) built on a cross-layer KV-sharing topology (v4_modules/cross_layer.py, share-kv/index/index-k). Vocabulary to be unpacked in Lesson 0004 using model_executor/models/deepseek.py + v4_modules/ as lab specimens. Correction from a repo audit: DSML marker handling lives in the external deepseek-recipe repo, not DeepInfer (Q&A §SWA KV, §bounded replay).

C3SWA bounded replay — the cleverest trick

The sliding-window state can't be kept for 72 hours economically. Trick: on a cache hit with a missing SWA window, recompute only the last 128 tokens, back off one 128-block if the window misses (hit length rule: L₁ possibly −128, capped at L−134), cutting cost to a constant independent of context and layers. Decoder-side it nearly halves prefill compute (Q&A §bounded replay). Env knobs: DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact, DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140. Lesson 0005 walks it with the examples/yoco/ code.

C4DSpark: verify the drafts worth verifying

Fixed-length draft verification wastes compute on low-acceptance tokens. DSpark adds a confidence head predicting per-draft-token acceptance; scheduling picks the subset maximizing marginal return (measured: verified length 5.0 → 3.2–4.4 at unchanged accepted length 3.29; +4–7% at production operating point). Systems twist: when async step N+1 is scheduled, step N's confidences don't exist yet — so length is computed on-GPU by a TileLang kernel (cumprod + topk sort, fused remap) writing to a pinned buffer (Q&A §spec decoding). Lesson 0005b.

C5 Determinism is a feature you pay for

Batched GPU inference isn't bit-reproducible (reduction order changes with batch composition). DeepInfer offers batch-invariant mode (identical results regardless of batch: DEEPINFER_BATCH_INVARIANT=1) and deterministic sampling (fixed seq_seed, MTP off) — NV-only. Nuance from the repo walk: batch-invariance is on by default in the offline examples on NVIDIA (examples/offline_inference.py:43) while the eval runner labels it "(slower)" — reproducibility is a default, not an opt-in. Why you'd ever turn it off: throughput. Why you'd want it: debugging, evals, reproducible research.

C6 EPD disaggregation & storage as a first-class engine

1P+1D deployable; realistic units 64+64 GPUs. With the KV cache decoupled to B5's 3FS store, prefill machines don't need affinity — "engines pull work by remaining compute quota" and prefill cost is solved per step by a fitted quadratic cost model under a nanosecond budget (Q&A §prefill LB). You'll meet that scheduler in Lesson 0002.

5 · Tier D — The codebase map — the DAG's leaves

built on: everything above

D1Boot path & the native scheduler

entrypoints/llm.py (LLM) → engine/llm_engine.py (LLMEngine; _init_workers, _init_cache, _create_scheduler) → worker/model_runner.py (ModelRunner) → model_executor/models/deepseek.py. Scheduler: native, stubbed in deepinfer/_C/engine.pyi. Your assignment today is to trace exactly this spine in assignments/0001-trace-boot-path.py. The full map lives in Reference 0001.

D2 Model execution layer

models/deepseek.py (DeepseekForCausalLM) + v4_modules/ (the novel V4.1 pieces) + mtp/ (draft/MTP) + layers/: attention_backend.py, sampler.py, layernorm, rotary_embedding, tilelang_ops/ (incl. *_zos.py async-scheduling kernels and Ascend twins), mtp_info_pool.py, eplb/, input_metadata/.

D3 Kernels: vendor + csrc + TileLang

vendor/ submodules = FlashMLA (attention), DeepGEMM (GEMM; FP8/FP4), DeepEP (MoE comm), DeepSelect — each with an Ascend mirror — plus hand-written TileLang in tilelang_ops/ and C++ glue in csrc/. Per the Q&A, internal versions differ from public ones by ~5% end-to-end.

D4 Async/verify plumbing ("zos")

worker/zos_status.py, sequence.py GPU-resident buffers for sampled tokens / MTP predictions / confidence rates ("D2D in zos"), dflash_cuda_graph_runner.py (DFlash = the draft-model graph runner). Read together in Lesson 0005b once spec decoding is solid.

D5 Peripherals with lessons of their own

ve/ vision processing (EPD's third leg), structure_output/ (grammar compiler → per-step masks), distributed/, deep_cluster/ (hardware/topology binding), hugging_face/ (loading). Secondary lessons; each short.

D6 Measurement: benchmarks & evals

examples/benchmark.py (carefully decoupled prefill/decode metrics; profiler sections; full-acceptance accounting — read examples/README.md before trusting any number), examples/sweep/, eval/ (AIME, GPQA, HLE), PPL baselines as golden tests (tests/models/offline_decode_ppl.json). Lesson 0006.
